Ubuntu 24.04 安装 3X-UI 3.7.0：REALITY、Hysteria2 与 VLESS-WS 配置笔记

记录一下 Ubuntu 24.04 VPS 安装 3X-UI 3.7.0 的过程，以及三种入站的配置：VLESS + TCP + REALITY、Hysteria2、VLESS + WebSocket + TLS。

本文按现有入站整理成可复用步骤。域名统一替换为 node.example.com，UUID、密码和密钥需要重新生成。文中的命令在 VPS 的 Ubuntu Bash 终端执行，不是在本地 Windows PowerShell 中执行。

下图来自已搭建的 3X-UI 3.7.0 面板。截图中的节点标识、域名、路径、密码等已遮盖，正文使用示例值；截图展示原有配置，基础搭建建议以各节文字说明为准。

一、先规划域名和端口

准备一台 Ubuntu 24.04 VPS、可使用 sudo 的 SSH 账号，以及一个自己管理的域名。给 node.example.com 添加 A 记录，指向 VPS 公网 IPv4。只有服务器确实能使用 IPv6 时才添加 AAAA 记录。

本文采用直接连接 VPS 的方式。使用 Cloudflare DNS 时，节点域名设为 仅 DNS（灰云）。

用途 端口 协议 说明
SSH 实际 SSH 端口，通常为 22 TCP 启用防火墙前先放行
HTTP-01 证书验证 80 TCP 本文使用 standalone 申请及续期
3X-UI 面板 自定义，例如 2053 TCP 与三个入站端口分开
VLESS + REALITY 443 TCP 不需要自己的域名证书
Hysteria2 10001 UDP 使用域名证书
VLESS + WS + TLS 10002 TCP 使用域名证书
Hysteria2 跳端口，可选 48000–50000 UDP 还需要转发到 10001

VPS 厂商的安全组和 Ubuntu 的 UFW 是两层规则，上述需要从公网访问的端口，两边都要放行。面板端口建议只允许自己的管理公网 IP。

2. 配置面板 HTTPS 和续期

在面板设置中填写完整证书链和私钥路径，保存并按提示重启。后续使用安装器或面板显示的 HTTPS 地址访问。

确认有 acme.sh 的定时任务。本文使用 HTTP-01 standalone，后续续期仍需要 TCP 80 可访问且可被验证程序绑定。以后增加 Nginx 占用 80 时，应同步调整验证方式，不能只看第一次申请成功。

续期重启 x-ui 会短暂影响连接。若自行修改过服务运行用户，还要确认该用户能读取证书和私钥。

五、VLESS + TCP + REALITY

在入站列表中新建入站，按以下字段填写：

字段 配置
备注 reality-demo
协议 VLESS
监听地址 留空，使用默认监听
端口 443
UUID 在面板中新生成
Flow 留空，与原配置一致
Decryption / Encryption none / none
传输 TCP，部分内核称 RAW
TCP 伪装 none

图中保留原配置的最小客户端版本供对照；密钥区域未纳入截图。原配置使用 Cloudflare 目标站，并填写了多个 SNI。整理笔记时不要把这些域名当成通用模板：先检测目标站支持 TLS 1.3 和 H2，并确认 SNI 与目标站证书及握手行为匹配。 未确认的 SNI 不加入列表。

另外，REALITY 会把未通过认证的连接转给目标站。官方特别提醒使用 Cloudflare 等 CDN 目标可能带来转发滥用问题，选目标时应考虑这一点。字段含义见 REALITY 配置说明 和 目标站选择说明。

原配置的 minClientVer: 1.8.2 不代表所有客户端都适用；它限制的是 Xray 内核版本。新建时按当前内核默认设置和实际客户端兼容性配置，不盲目沿用旧值。

嗅探可沿用原配置：开启，目标覆盖选择 http、tls、quic，并开启 routeOnly。

客户端需要对应什么

保存后用面板生成的分享链接或二维码导入，再检查：

  • 服务器：VPS 公网 IP，或直连 VPS 的灰云域名。
  • 端口：443；协议：VLESS；传输：TCP/RAW；安全：REALITY。
  • UUID：与服务端一致。
  • SNI：服务端 Server Names 列表中的一个有效值。
  • Public Key：服务端公钥；Short ID：服务端列表中的一个值。
  • Fingerprint：chrome；Flow：与服务端一致，本文留空。

私钥只保留在服务器端。若要启用 xtls-rprx-vision，需要两端一起修改，不能把留空的配置写成“已经启用 Vision”。

六、Hysteria2 入站

3X-UI 中协议名称是 hysteria，版本为 2，分享链接使用 hysteria2://。不能因为协议名没有数字 2，就改装另一套 Hysteria 服务。对应关系可以在 3X-UI v3.7.0 数据模型 中核对。

1. 先配置固定端口

字段 配置
备注 hysteria-demo
协议 / 版本 hysteria / 2
端口 10001，UDP
客户端认证 Auth 新生成的强密码
传输 / 版本 hysteria / 2
UDP Idle Timeout 60
安全 TLS
Server Name node.example.com
证书 / 私钥 上文两个固定路径
ALPN h3
Salamander 开启时生成独立混淆密码
Sniffing 关闭，与原配置一致

图中的 Password 是 Salamander 混淆密码。用户 Auth 在客户端管理中设置，并不在此处填写。

原导出中的 auth、password 和 Salamander 的 password 不要混用。Hysteria 用户认证使用客户端记录的 auth；Salamander 是额外的混淆密码，两端都要一致。共享用户记录可能带有其他协议的字段，不代表它们都参与当前协议认证。

原配置使用 finalmask.quicParams.congestion: bbr，可以作为已有配置记录保留。QUIC 的 BBR 与系统 TCP BBR 不是同一项开关。

原窗口参数为流窗口 8388608、连接窗口 20971520，空闲超时 30、KeepAlive 10、最大入站流 1024。首次搭建可先用面板默认窗口值，连通后再按需要调整，不把这些数字当成任何 VPS 都适用的提速参数。参见 Xray Hysteria 传输 和 FinalMask 配置。

2. 客户端配置

先关闭跳端口，用固定 10001 验证：

  • 服务器：node.example.com；端口：10001；协议：Hysteria2。
  • 认证密码：服务端用户 Auth。
  • SNI：node.example.com；ALPN：h3。
  • 开启证书校验，不启用 Allow insecure / 跳过验证。
  • 如果服务端启用 Salamander，客户端也选择 Salamander 并填相同混淆密码。

优先导入面板分享链接，检查当前客户端是否支持 Hysteria2、混淆和跳端口参数。TCP 连通测试不能验证 UDP 节点是否可用。

3. 可选：48000–50000 端口跳跃

原配置中的 udpHop.ports 为 48000-50000，interval 为 5-10。不能只保存这一项、放行一段端口，就认定服务端的跳端口链路已经完成。

本文采用明确的路径：客户端访问 48000–50000/UDP，服务器将这些端口转发到 Hysteria2 的 10001/UDP。 先检查是否已有面板或系统规则，避免重复配置。官方 Hysteria 独立服务的自动跳端口功能，不等于所有 Xray 安装都会自动创建同样的规则。

厂商安全组同步放行这段 UDP 端口。使用 UFW 管理持久规则时，可以在 /etc/ufw/before.rules 的 *filter 块前增加一个独立 NAT 块；如果已有 *nat，把规则合并到已有块中，不要覆盖原文件：

ens3 是示例网卡名，先运行 ip route show default 查看实际公网入口网卡，再替换。使用 IPv6 时，在 /etc/ufw/before6.rules 配置相应规则，并确认 IPv6 UFW 已启用；只使用 IPv4 时无需添加 IPv6 节点解析。

这里转发到本机监听端口，不需要为它开启跨主机 IP forwarding。不要同时叠加多套 UFW、iptables-persistent 和独立 nftables 持久化管理。

客户端还要实际设置端口范围及跳跃间隔，或确认导入链接保留了这些选项。若客户端不支持随机 5-10 秒区间，可在其支持的设置中使用固定间隔，例如 10 秒。用真实客户端连接后查看 NAT 计数，并在重启 VPS 后再次测试。转发原理见 Hysteria 官方 Port Hopping 文档。

关于 Cloudflare 和 ECH

当前 10002 是直接访问 VPS 的端口，不在 Cloudflare 标准 HTTPS 代理端口列表中，所以本文使用灰云。以后若接橙云，需要重新规划 Cloudflare 支持的入口端口，以及源站与证书策略，不能只切换 DNS 开关。参见 Cloudflare 支持的代理端口。

原导出还带有 echServerKeys 和 echConfigList。它们属于可选 ECH 配置：先不填，完成普通 WS + TLS 连通测试；确实需要 ECH 时，再使用兼容客户端生成和配置新的配套参数。服务端 ECH 密钥不能贴进公开博客，也不要使用原导出中的密钥。

八、原始 JSON 中哪些内容不需要照抄

面板导出的对象含有数据库信息、用户管理字段、统计值和客户端分享参数，并不是完整的 Xray config.json，不能直接整段覆盖到内核配置文件。

字段 笔记中的处理
up、down、clientStats、时间戳 运行统计，不写入搭建模板
id、userId、nodeId、originNodeGuid 由目标面板管理
UUID、subId、Auth、密码 重新生成，不公布原值
REALITY privateKey、ECH 服务端密钥 不公开，重新生成
REALITY publicKey、Short ID 与新生成的服务端配置配套
域名和证书路径 替换为自己的实际值
流量配额和重置字段 在面板按实际需求设置

原用户额度 1073741824000 字节相当于 1000 GiB。原记录同时出现入站不重置、用户月度重置和旧的 reset 字段，不宜直接用一个字段判断最终结算规则。若希望每月 4 日重置，在 3.7.0 面板对应用户的重置设置中明确选择并核对显示结果。

九、检查是否真正搭建完成

确认 REALITY 的 TCP 443、WS 的 TCP 10002 和 Hysteria2 的 UDP 10001 有对应监听。面板运行正常不代表每条入站都已经连通。

WS 的证书可以这样检查：

普通 openssl s_client 不能完成 Hysteria2 的 QUIC 验证，也不能用来认证 REALITY 节点。最终分别导入三个节点，进行真实访问并观察客户端日志和流量统计；有跳端口时，再额外检查转发命中及重启后的连接。

现象 优先检查
开 UFW 后 SSH 连不上 SSH 真实端口是否提前放行；必要时使用厂商控制台修复
面板正常，节点都不通 安全组、UFW、内核日志、是否监听正确地址
REALITY 不通 UUID、公钥、Short ID、SNI、Flow、系统时间
Hysteria2 超时 是否放行 UDP；Auth 和混淆密码；运营商是否限制 UDP
固定端口通，跳端口不通 范围放行、NAT、入口网卡、客户端参数、IPv4/IPv6 是否一致
WS 连接失败 域名解析、证书、Path、Host、SNI、ALPN
开启橙云后失效 是否使用 Cloudflare 支持的协议和端口
过一段时间证书失效 acme.sh 定时任务、80 端口、续期部署和重载日志

这份笔记根据现有配置、实际面板截图和官方资料整理，未在新的 Ubuntu VPS 上重新执行全流程；实际部署以本机版本、日志和三个节点的真实连接结果为准。
